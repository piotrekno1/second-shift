# SecondShift 0.1.0b16

## Upgrade from beta 15

- Take a backup and follow the usual
  [update steps](../production-deployment.md#update-and-back-up). The release
  has twelve new migrations in `connections`, `runs` and `runner`. They run
  with the others, so the update needs no other database step.
- **Replace `compose.production.yaml` with this release's copy.** Agents
  no longer reach the gateway. Their tool calls go through the egress proxy
  to the runner, and the worker collects them from there. The gateway leaves
  the agents network, and a new internal `relay` network joins only the
  runner and the egress proxy. If you edited the Compose file, bring your
  edits over to the new one. `compose.env` needs no change. A leftover
  `AGENT_GATEWAY_ADDRESS` is ignored.
- If you use Claude Code or Codex logins, rebuild the agent image after
  `dc pull`, as the update steps say. The new image reports the models a run
  used and accepts a chosen model.
- With `secondshift up` or a `pip` install, nothing changes for you.

## Several runners

A control plane can now send runs to more than one runner, for example a
second machine with more memory or a different sandbox. See
[Runners](../runners.md#how-runs-are-placed).

- `compose.runner.yaml` runs a runner on another host, with its own
  PostgreSQL, egress proxy and Caddy for HTTPS. `secondshift runners add`
  registers it with its own token. `runners list`, `drain`, `activate` and
  `remove` manage the registry. The runner in `SECONDSHIFT_RUNNER_SERVICE_URL`
  stays registered as `default`.
- A run goes to an active runner that offers its environment and has a free
  session. The one with the most free sessions wins. A run stays on its
  runner until it ends.
- Each subscription login has a home runner, so Codex token refreshes stay
  in one copy. It moves only when that runner drains, goes down or lacks the
  environment. Removing a login removes its copy from every runner.
- Added runners must use HTTPS and a token no other runner has. The control
  plane pins each runner's provisioning key, so logins are sealed only to the
  runner it registered.
- The worker checks every runner. One that stops answering takes no new
  runs. After 10 minutes its runs fail as runner failures and name it.
  Sessions it missed are stopped once it answers again.
- **Settings → Runners** (staff only) shows each runner's state, its runs
  and session limit, its environments, whether it can run Claude Code and
  Codex, and its key fingerprint. Run details name the runner when there is
  more than one.
- `SECONDSHIFT_RUN_CONCURRENCY` caps runs across all runners, so raise it
  when you add one.

## Subscription logins

- **Choose a model.** A login's owner can pick **Default**, **Opus**,
  **Sonnet** or **Haiku** for Claude Code, or enter a full model name under
  **Other…**. Codex offers **Default** only. Runs use the model chosen when
  they were planned. Repository configuration never chooses it.
- **See which models ran.** The run page shows the models Claude Code
  reported, including the small model it uses for its own chores. A login's
  check names the model that answered. Codex reports none, so its runs show
  the chosen model.
- A plan that can't use the chosen model fails the check with "this plan
  cannot use opus", and runs point to **Models**. The login is not marked
  refused.
- **Jobs on one login run in parallel.** Before, a second job on a login that
  was already running failed. Each Codex run now keeps its own state and
  shares only the login file, so a token refresh reaches the other runs.

## Security

- Agents' tool calls reach the control plane only through the runner, on
  every server. Nothing on the agents network can reach the gateway, which
  holds model keys and has the database open.
- The model gateway checks each call against the models frozen into the
  run's plan. Before, editing a provider's model list changed what a running
  job could call.

## Smaller changes

- A run keeps one MCP session with each custom MCP connection, from its first
  call to its end, so servers that keep state per session, such as Playwright
  MCP, keep it between calls. If the server drops the session, the run starts
  a new one once and its timeline says so.
- The Overview checklist stays until the first run succeeds, including
  through failed or canceled attempts, and links to the run.
- The docs show how runners, the relay and the gateway fit together.

## Fixes

- A runner behind a proxy that answers 502, 503 or 504 now fails its runs as
  runner failures, not skill failures.

## For contributors

- Development needs uv 0.13.8 or newer. CI installs from the lockfile only,
  builds without build isolation, and waits seven days before taking a new
  dependency release.
- The dashboard's API types are generated from the OpenAPI schema.
