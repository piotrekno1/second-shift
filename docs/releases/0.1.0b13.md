# SecondShift 0.1.0b13

## Upgrade from beta 12

- Rebuild the separate subscription agent image from this release and update
  `AGENT_IMAGE`. Its files moved from `secondshift/runner/agent_image` to
  `secondshift/agent/image`, and the runner now starts
  `secondshift.agent.image.agent`. A runner from this release cannot start an
  agent image built from beta 12. Build it with
  `dc run --rm --no-deps runner python -m secondshift.agent.build --tag secondshift-agent:production`,
  as in [subscription setup](../production-deployment.md#optional-subscription-agents).
  The image now installs its CLIs from a lockfile with checksums.
  Let subscription runs finish before upgrading.
- Subscription agents now reach the internet only through an egress proxy
  that allows their provider's hosts. On a server, the agent network becomes
  internal and Compose adds an `agent-proxy` service. Docker can't change an
  existing network, so remove it once with `dc down` before `dc up -d`. If
  `AGENT_SUBNET` isn't the default, set `AGENT_PROXY_ADDRESS` in `compose.env`
  to a free address inside it. `secondshift up` creates the internal
  `secondshift-agents` network and a `secondshift-agent-proxy-<gateway port>`
  container by itself. A runner that sets `SECONDSHIFT_AGENT_NETWORK=bridge` must remove
  it, because the runner refuses a network with a route out.
- `SECONDSHIFT_AGENT_RESOLV_CONF` is gone. Agents no longer look up names, so
  you can delete `agent-resolv.conf` from `RUNNER_ROOT`. A runner ignores the
  variable if it is still set.
- `secondshift up` builds the new agent image by itself. If it says it couldn't
  update the agent image and is using the last one built, subscription runs
  fail until a build succeeds.
- Sandbox images now come only from the runner's env, one per sandbox, as
  `SECONDSHIFT_SANDBOX_<NAME>`. `SECONDSHIFT_SANDBOX_DEFAULT` names the one
  jobs get when they name none. `SECONDSHIFT_RUNNER_IMAGE` is gone, and a
  runner that still has it refuses to start and says how to rename it.
  - On a server, add the defaults to an existing `runner.env` once, as in
    [production deployment](../production-deployment.md). To keep a custom
    image, name it `SECONDSHIFT_SANDBOX_<NAME>` and point
    `SECONDSHIFT_SANDBOX_DEFAULT` at that name.
  - A server now requires every sandbox image pinned by digest, the default
    included.
  - `secondshift up` adds the defaults to its `runner.env` by itself.
  - The web app, gateway and worker no longer read sandbox images. Delete
    `SECONDSHIFT_RUNNER_IMAGE` from their env files if you set it there.
- Each sandbox command now runs under `timeout`, so a command past its limit
  ends inside the sandbox and the agent can carry on. Every sandbox image
  needs a `timeout` command. Debian,
  Ubuntu and Alpine images have one. Without it, a command past its limit
  still stops the sandbox and ends the run.
- With PostgreSQL, the gateway now keeps a pool of database connections, up
  to `SECONDSHIFT_DB_POOL_MAX_SIZE` per process (default 20). The gateway and
  the runner ignore `SECONDSHIFT_DB_CONN_MAX_AGE_SECONDS`, and
  `SECONDSHIFT_RUNNER_DB_CONN_MAX_AGE_SECONDS` is gone. You can delete either
  from their env files.
- Sandboxes now allow 1024 processes, up from 256, and each command 300
  seconds, up from 120. Threads count as processes, and a project's full
  checks needed more. A server that set `SECONDSHIFT_RUNNER_PIDS_LIMIT` or
  `SECONDSHIFT_RUNNER_COMMAND_TIMEOUT_SECONDS` keeps its own values.
- Repository syncs now run in the worker. **Resync** and adding a repository
  return at once with `syncing: true`, and the page shows **Syncing…** until
  the worker finishes. A script that reads jobs right after either call should
  wait until `GET /api/repositories/{id}` shows `syncing: false`. The MCP
  `sync_repository` tool waits up to a minute and returns `syncing` if the
  sync is still running. Imports no longer need a longer web timeout.
- **Validate configuration** and `POST /api/repositories/{id}/validate` are
  gone. **Resync** runs the same check and applies the result. The
  repository's `validation` in `GET /api/repositories/{id}` shows what the
  last sync found.
- GitHub tools gain `search_issues`, `list_issues` and `issue_read`. The
  worker lists each GitHub and Sentry tools connection's tools again within an
  hour of starting, so jobs can request the new tools. To read issues, the
  GitHub App needs Issues read access, and a personal token needs Issues
  read. Filing issues needs read and write. Accept the App's new permission
  on each installation, or edit the token. Then run **Check access** on the
  GitHub connection.

## Review then fix

- Jobs can search, list and read issues in their own repository with
  `search_issues`, `list_issues` and `issue_read`. Search stays inside the
  job's repository, and sub-issues aren't read.
- A job that files issues and may call `search_issues` is told to look for an
  existing issue, open or closed, before proposing one.
- A new example, `examples/issue-fixer`, fixes one issue a maintainer labeled
  `fix-approved` per run and opens a draft pull request that closes it. It
  skips an issue that an open pull request already closes. It runs in the
  `python_node` sandbox, because its checks need Python and Node.
- SecondShift's own repository runs a monthly code review that files issues,
  and the issue fixer on weekdays.
- A draft pull request takes its title from the report's first `# ` heading,
  so a job that fixes a different issue each run gets a title for each. With
  attribution off, the branch is named after that title too. Reports without
  a heading keep the job's name.
- The agent is told which commit its sandbox holds, so reports name the
  repository's commit, not the sandbox's own.
- With **Mention SecondShift** on, draft commits name `secondshift-bot` as a
  co-author. GitHub then lists SecondShift among the repository's
  contributors once one merges. With it off, nothing names SecondShift.
- The fixer takes only fixes that are quick to review. It hands an issue back,
  with no pull request, when the fix needs a migration, changes more than
  about 80 lines or 3 files, changes concurrency or crash handling, or needs a
  design choice. Its report says why and suggests a plan.
- A job names the label that approves issues for it in `approved_issues`, with
  a `hand_back` label, so the skill doesn't name one. The agent can hand one
  approved issue back per run. SecondShift then comments on the issue with the
  agent's plan, removes the approval label and adds the `hand_back` label. It
  acts only on an open issue that still has the approval label. The run page
  shows **Handed back** and links the comment, with no skipped draft beside
  it. It needs **Allow issues** on the repository.
- A fixer draft opens with its risk, whether the checks passed, and where to
  look in the diff.
- Footers on drafts, issues and hand-backs link the run's page, or name it as
  "run 12" when the dashboard runs on localhost. They wrote "run #12", which
  GitHub linked to issue 12.
- Draft descriptions name files by their repository path. Links to sandbox
  paths, which led nowhere on GitHub, become plain paths.
- When CI waits for review, a draft's description says CI hasn't run on it.
- Jobs that propose issues start each one with how likely the problem is, what
  it costs, and how big the fix is.
- Close a fixer's draft and keep `fix-approved` to ask for another attempt.
  The fixer reads the closed draft's comments and reviews first and says what
  it does differently, so say there why you closed it. With no reason from a
  person, or after two closed drafts, it hands the issue back. The example
  now requests `pull_request_read`, which an owner approves once.

## Sandboxes

- A job picks a sandbox by name with `environment: <name>` in
  `.secondshift.yaml`. Jobs that name none get the default.
- New installs offer `python`, Docker's official `python:3.13-slim`, as the
  default, and `python_node`, with Python 3.13, Node 24, git and make, for
  jobs that run a project's full checks. Both are pinned by digest. Add a line
  to `runner.env` to offer another image, or remove one to stop offering it.
  A new release never changes the file. See
  [sandboxes](../self-hosting.md#sandboxes).
- Only the runner maps a name to an image. The web app and worker ask it which
  sandboxes exist, and a run sends just the name.
- Settings shows the default and each sandbox with its image and env var.
- A job that names a sandbox the runner doesn't offer can't be enabled or run.
  **Finish setup** on the repository and the job's page say so, and name the
  env var that adds it.
- When the runner's settings stop `secondshift up`, it now prints why, such as
  how to rename `SECONDSHIFT_RUNNER_IMAGE`. It used to say only "Couldn't
  prepare runner data".

## Fixes

- A command that ran past its limit stopped the whole sandbox and ended the
  run. Now only that command ends, and the agent gets a timed-out result.
- A new `SECONDSHIFT_RUN_CONCURRENCY` took effect only on the second worker
  restart. It now applies on the first.
- A Codex run whose login could no longer refresh its token failed with "The
  agent could not finish". It now says the sign-in expired and to reconnect
  the subscription. This lives in the agent image, which this release
  rebuilds anyway.
- The setup proxy closes a registry connection that sends nothing for 60
  seconds. A stalled download now fails setup in about a minute instead of
  hanging until the setup time limit. Change it with `--idle-seconds`.
- The gateway leaked a database connection for each request and held one for
  the length of every model stream. After many runs Postgres refused new
  clients. Connections now go back to the pool, and a stream holds none.
- A worker restarted during a run kept running next to the new one, and both
  ran the same run. The old worker now exits once it stops waiting. The run
  it was in fails with a clear reason and isn't run twice.
- A subscription run that failed for its login, such as an expired sign-in,
  now links to that login on **Models**.
- A schedule with a sixth field, or a date that never comes such as 31
  February, passed validation, but the scheduler can't run it. One such job
  stopped every job's schedule from syncing. Schedules now need exactly five
  fields and a next run. A stored job with a bad schedule is skipped with a
  warning, so the others still sync. `@daily` and similar names are refused.
- A job run saved by a process that stopped before queueing it stayed queued
  forever. The worker now queues it.
- Only 500 active runs were checked for an ended workflow, so a long backlog
  could hide older ones. Every active run is now checked.
- A notification retry that DBOS accepted went back to failed if closing the
  DBOS client failed, so a second retry could send it twice. It now stays
  retrying.
- A database error in a periodic task's enabled check stopped the worker's
  other periodic tasks. It's now logged, and the others carry on.
- After Postgres restarted, the worker kept its broken database connections
  and its steps failed until it restarted. It now replaces them before each
  step.
- A worker stopped while it was waiting on a lock, or in the middle of a git
  fetch, didn't exit. A second stop signal could deadlock it too. It then held
  the repository's mirror lock, and every later sync of that repository hung.
  The worker now stops at once.
- A local repository's page and settings fetched every linked skill on each
  request. With many linked skills a page took over 30 seconds to load. Now it
  reads only the branch head. Resuming a repository now checks what the last
  sync found instead of reading everything again.
- **Resync** and adding a repository ran the whole sync inside the web
  request. A sync with many linked skills took 40 seconds, held up other
  requests, and hung until the request timed out when another sync held the
  repository's lock. The worker now runs every sync, one at a time, and the
  page updates when it finishes.
- A sync asked GitHub about a linked skill's repository once per skill. It
  now asks once per repository, several at a time. A sync of 69 linked skills
  went from 36 seconds to 5.
- A GitHub repository whose first sync failed was removed again, with only
  an error message left. It now stays, and its page shows the problem, as a
  broken manifest already did.
- A cron tick already queued when a job's schedule was removed created a run
  and then failed. The worker later queued that run, so the job ran without a
  schedule. The tick now checks the schedule before creating anything.
- A worker that stopped right after skipping a cron tick, because the last
  run was still going, could run that tick anyway when it restarted, or
  record the skip twice. The restarted worker now finds the skip it already
  recorded.
- When an OpenAI model stopped at its output token limit, the gateway
  recorded no usage for that request. The run's token count and budget missed
  those tokens. The gateway now reads usage from incomplete responses too.
- Retrying a failed delivery failed on PostgreSQL with a database error. It
  now works.
- `secondshift up` said "Preparing the agent image. The first start takes a
  few minutes." on every restart. With an image already built, it now says
  "Checking the agent image."
- The Overview checklist marked "Choose what runs jobs" done once any model
  key or subscription was saved, even when none ran jobs. It now stays open
  until one is chosen.
- On Settings at tablet width, a long env var ran past its card and the page
  scrolled sideways. On a phone, card links such as "All jobs needing
  approval" wrapped beside the heading. Content no longer shifts sideways
  between short and long pages.
- The GitHub check said "Reaches all 2 repositories" and a job's spend said
  "across these 1 runs". They now say "both repositories" and "for this run".
- `secondshift --version` printed Django's version. It now prints
  SecondShift's.
